# Supabase architecture analysis

The reference is an internal operations portal with a companion mobile app and a smaller web application. The main portal is a React 19.2.7 SPA built with Vite 8.0.16 and TypeScript 6.0.3. Its committed lockfile pins Supabase JS 2.107.0, TanStack Query 5.101.0 and React Router 7.17.0. Flutter pins supabase_flutter 2.17.2. No Next.js application was found. Checked-in infrastructure includes Nginx config, release automation and database/backup/demo/monitoring/restore tooling. Endpoint topology, platform versions, active deployment settings and operational outcomes require independent evidence.

| Evidence | Source-supported observation | Reusable decision |

| S01 | Web bootstrap validates Vite URL and browser key before creating a singleton. It explicitly uses browser storage, PKCE, refresh and URL-session detection. | Validate configuration and scope browser singleton ownership. Use request-scoped cookie clients in SSR. |

Forced password change and phone verification/recovery flows exist. | Separate identity, application profile, permission checks and UX. Keep cache tied to current identity. |

The inspected flows comprise password login and profile fetch, folder browsing and file upload, participant messaging, and data import/export. The repo contains several platform and domain surfaces beyond these representative flows. Static evidence establishes intended seams and specific checked predicates. It provides no deployed grants, data cardinality, backup success or exhaustive replay guarantee.

## Source capability distinctions

- Observed identity work includes passwords, session refresh, sign-out, first-login profile completion and custom phone verification/recovery. Public sign-up, native Supabase magic link/OTP, browser OAuth, general account deletion, MFA, SSR cookies and provider settings were not established by the inspected flows.
- Organizational access is observed. The proposed SaaS tenant model is an alternative, with no claim of full end-to-end tenant isolation in the reference.
- View evidence is available. Materialized views, a general Postgres concurrency strategy and independently verified schema drift were not established.
- Postgres Changes is observed. Broadcast and Presence guidance comes from official documentation.
- Public website content functions are present. An App Router server client or combined React and Next deployment is a proposed profile.

## Authoritative recommendations

- Local CLI flow, reproducibility and type generation. [Supabase CLI workflows](https://supabase.com/docs/guides/local-development/cli-workflows)
- Cookie-backed browser/server setup and versioned refresh entry point. [Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client?framework=nextjs&queryGroups=framework) · [Next.js Proxy](https://nextjs.org/docs/app/getting-started/proxy)
- Database role grants, trusted metadata, and security policy tests. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) · [PostgreSQL CREATE FUNCTION](https://www.postgresql.org/docs/current/sql-createfunction.html)
- Object and signed-URL authorization, private channels, and function identity. [Storage access](https://supabase.com/docs/guides/storage/security/access-control) · [Realtime authorization](https://supabase.com/docs/guides/realtime/authorization) · [Function authorization headers](https://supabase.com/docs/guides/functions/auth-headers)

## Order and replay prerequisites

S12 parses the original snapshot and all 206 committed migrations as top-level PostgreSQL grammar. The release ledger contains 200 names and six files are outside it. Comparing the ledger-based projection with filename order changed 49 positions, but retained the same projected policy and function definitions. This does not prove the original release history or the final live state.

Review before executing. The history includes foreign servers/tables and schema imports, trigger and procedural code, role-level settings, data importing and destructive statements. Six files matched outbound or integration indicators. Sixty-two files including the snapshot mention managed schemas. Fifty-four match sensitive or environment-bound indicators. These are review leads, including comments and embedded function bodies. They do not establish credential exposure or actual network activity. The earliest compatible schema and provider-managed objects are not proven. An isolated replay needs a sanitized starting catalog, an approved migration-by-migration allowlist, scrubbed data fixtures, disabled runtime egress, and stubs or omissions for external dependencies. Preserve those omissions in the replay log. See the [completion report](PHASE_3_VALIDATION_COMPLETION.md).
