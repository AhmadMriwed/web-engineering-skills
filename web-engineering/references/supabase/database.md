# Database, contracts and migrations

Model examples from [the neutral fixture](../../assets/supabase-example/README.md) and apply WEB-SUP-001 and WEB-SUP-002.

- Model ownership explicitly. Use a stable primary key, foreign keys with deliberate deletion behavior, and a unique FK for one-to-one. Use a child FK for one-to-many and a junction with a composite primary or unique key for many-to-many. For tenant relationships use tenant-aligned composite FKs to prevent cross-tenant references. Choose UUIDs for independently generated identifiers, identity columns when sequence semantics fit. Use numeric or integer minor units for exact quantities, `timestamptz` for instants, and explicit nullable semantics. Use enum for stable closed states and a referential table for configurable values.
- Enforce invariants with NOT NULL, CHECK, unique and foreign key constraints. Match case and collation requirements when defining uniqueness. Use meaningful database defaults and server-managed audit timestamps. If soft deletion is required, make it explicit in RLS, uniqueness, relationships, reporting, and retention. Normalize first. Document reconciliation and write ownership for derived fields. Use triggers for invariants across all writers, avoid hidden external side effects. Use a view for reusable read projection and validate caller permissions with security-invoker support where available. Use materialized views when measured refresh and freshness bounds justify them and restrict direct grants.
- Index tenant/ownership lookups, child FK columns and common filter+order paths where plans justify them. Use composite order aligned with query predicates and stable tie-breakers. Read EXPLAIN plans with synthetic cardinalities. Run EXPLAIN ANALYZE for mutations only in disposable data or managed rollback. Monitor bloat, locks, connection pools and slow queries after rollout.
- Project selected columns and relationships, paginate with a bounded limit and stable ordering. Use range for small lists and keyset for deep or high-churn lists. Choose count accuracy explicitly. Normalize SDK and domain errors while redacting details from UI and logs. Review empty results, unauthorized operations and cardinality separately. Propagate cancellation where the SDK supports it. Debounce inputs, keep filters in URL where useful, and scope query keys by identity, tenant and filters. Invalidate affected reads after committed writes. Use optimistic updates only with rollback and reconciliation semantics.
- Validate form and imported inputs before sending. Generate table Row, Insert and Update types, enum, relationship and RPC types from migrations. Bind `createClient<Database>` to generated types in strict TypeScript. Map view models and runtime-validate JSON/RPC/external responses where static types cannot prove the shape. Avoid raw SQL interpolation and constrain dynamic filter syntax to allowed fields and operators.
- Use database functions for atomic multi-row changes. Use an optimistic version condition, explicit lock or stronger isolation according to the invariant. Retry serialization conflicts only with bounded, idempotent operations. Choose explicit upsert conflict targets and check both insert and update policies. For bulk work define all-or-nothing versus per-item results, stable dedupe keys, bounded chunks and auditable retries. For imports stage, validate and preview before committing. For exports reauthorize columns and rows, cap scope and expire artifacts.

## Change and release procedure

Pin CLI and runtime capabilities. Run `supabase init` in the approved repository and commit the reviewed configuration, which the pinned CLI generates as `supabase/config.toml` or `supabase/config.jsonc`. Verify Docker or a compatible supported container runtime, local ports and isolated synthetic data before `supabase start`. Use `supabase migration new <name>` for unique versions. Local Studio edits can seed a reviewed diff. Inspect SQL for grants, managed schemas, extension dependencies and unintended changes. Treat an existing hosted schema as a separate authorized baseline acquisition, record migration history and compare schema drift before linking or resetting anything.

Run `supabase db reset` only against the authorized disposable stack, then `supabase test db`. Keep synthetic fixtures in `supabase/seed.sql` and exercise an upgrade path using an isolated snapshot of the previous release. Generate `supabase gen types --lang typescript --schema public` into a temporary file, review the diff and move it to the generated contract location after success. Check drift in CI using the same pinned toolchain. Test a second reset for reproducibility. For incompatible changes, expand, backfill with bounded resumable work, switch readers and writers, then contract after compatibility is proved. Review locks, timeouts, transaction compatibility, large data changes and recovery choices. Obtain explicit approval before destructive changes or production-impacting execution. Verify backups and restore procedures on disposable targets. Prefer forward repairs when old application versions can tolerate the expanded schema.

Confirm `db reset --help` and `gen types --help` against the pinned CLI. Both commands default to local in CLI v3. From the disposable project root, verify the intended local stack before reset and omit remote selectors. CLI v3 does not accept the legacy explicit `--local` forms for these commands.
