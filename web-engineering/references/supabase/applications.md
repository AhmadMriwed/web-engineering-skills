# React, Next.js and split applications

## React SPA

Keep the [React foundation](../react-dashboard.md). Initialize one configured browser client and one auth owner at app composition. Subscribe to auth changes, unsubscribe on teardown, separate startup from signed-out state and remove private caches on sign-out, identity or tenant changes. Treat responsive route guards and capability-based controls as navigation support. Build feature repositories with typed reads and mutations, forms with runtime validation and localized errors, and use TanStack Query when shared cache or background refetch warrants it. Place query keys and hooks at feature boundaries and keep loading, first-use empty, zero matches, stale and failure states distinct. Choose Realtime selectively. Keep file inputs and progress local to the feature, and defer bucket/object checks to trusted boundaries. Test route entry, session expiry, account switches, permission-negative calls, forms, cache and cleanup.

## Next.js App Router

Keep [native component and cache boundaries](../next/profile.md). Use `@supabase/ssr` with browser client for Client Components and per-request cookie-bound clients in server modules. Block browser imports of privileged code. Use `proxy.ts` on Next.js 16+ and `middleware.ts` for the equivalent on earlier App Router versions. Use an installed-version-supported verified identity operation such as `getClaims()` and persist refreshed cookies in the outgoing response and request context. Preserve refresh response cookies when redirecting or replacing the response. Local cookie session reads alone are not trusted authentication checks. Each protected data operation, Action and Handler independently checks identity and permission. Use `getUser()` where current Auth-server state is required. Layout guards help navigation, but access remains checked at each data boundary. Isolate public prerendering and locale metadata from private request rendering. Keep private authenticated data and Set-Cookie responses out of shared caches. Test both identities sequentially on the same URL and exercise refreshed cookies after redirects. Use account-specific storage URLs, localized form errors and browser-side subscriptions only in client islands. Verify callback origins, server hosting, routes and cache headers per deployment. [Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client?framework=nextjs&queryGroups=framework) · [Next.js proxy](https://nextjs.org/docs/app/getting-started/proxy)

## Combined system

Use a React admin and Next.js public app when cadence, ownership or hosting warrants split deployments. One Next.js app with route groups may suit a shared team, release and identity boundary. Share generated database types, stable versioned contracts and tokens with active consumers. Keep separate deployment configuration and explicit app permissions. Default to independent sessions with narrow cookie domains. Design cross-app identity deliberately through approved providers and allowlisted callbacks. Public clients receive only public projections. Admin UI never implies broad data permissions. Assign one migration owner, publish an app-to-schema compatibility window, deploy expand-before-consumers and contract after both consumers verify. Monitor environment segregation and rehearse rollback for each app. Choose a monorepo for coordinated edits or separate repositories with contract versioning for independent ownership.
