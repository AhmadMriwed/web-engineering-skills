# Next.js data, forms and security

Apply [shared engineering principles](../shared-core.md). A server page should call a server service directly when rendering needs data or credentials. Expose a Route Handler for a public HTTP integration, webhook or client-to-server boundary with a deliberate API contract. Use a Server Action for an application-scoped form or mutation, including its own validation and authorization. Avoid an internal HTTP hop from a server page to its own handler when both can call the same service. Use native Fetch for straightforward HTTP and framework cache control. Add an abstraction for common auth, deadlines, runtime decoding and standardized errors. Use Axios where an approved existing contract or a needed transport feature justifies it.

Keep server services in a clearly server-only module, and keep browser-safe endpoints and types separate. Confirm HTTP status, decode unknown data at trust boundaries, normalize recoverable errors, and allowlist filter/sort keys and limits. Forward abort signals for interactive queries. A cleanup flag can suppress stale writes and leaves network work running. Run independent calls concurrently, cap fan-out and pagination, and use bounded retry where operation semantics permit it. Validate upload size/type and authorize downloads. Keep mutation invalidation with its owner.

Use server-rendered data for initial content, URL for navigable filters, local state for drafts, and scope providers to cross-component needs. Add TanStack Query only when browser consumers need cache lifecycle, pagination, polling or mutation coordination. Define hydration and invalidation if sharing the result between server and browser caches. Source uses local hooks and URL search params, native Fetch and typed envelopes. Decoding, deadlines, retries, uploads, downloads and private session lifecycle require target evidence. See WEB-SRC-003 N04/N07/N08.

For contact or lead forms, put schema and mapping near the feature. Use React Hook Form and a resolver when complex local state or field errors justify it. Use native forms and Server Actions when progressive enhancement and server ownership fit. Define defaults, pending and duplicate-submit behavior, server field errors, success messaging and preservation of failed values. Validate on the backend, secure direct invocation and add abuse controls where appropriate. Optional dynamic fields, multi-step flows, file uploads and unsaved changes apply when required and need target tests.

Authenticate near data access and recheck authorization on each sensitive action, handler and external request. Proxy and UI guards can improve navigation. Restrict DTOs, cookies and redirects to intended trust boundaries. Use appropriate cookie flags and CSRF protections for cookie-backed writes, explicit CORS origins for cross-origin calls and safe allowlisted redirect targets. Keep credentials server-side, mark privileged modules server-only and audit client-exposed environment values. Avoid shared caching of private data, redact logs and sanitize approved rich markup. Use a server-side session and refresh contract when justified. The source is public-facing and shows a CMS sanitization seam. Protected sessions, Actions and Handlers are recommended alternatives with target verification. See WEB-SRC-003 N07/N08/N09 and [Next.js data security](https://nextjs.org/docs/app/guides/data-security).
